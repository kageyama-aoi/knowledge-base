Vercel VS GitHub Pages

Webアプリをどこに公開するか ── 二大プラットフォームを徹底比較

Section 01
概念説明 ── それぞれ何者か？
Vercel

Vercelは、フロントエンド特化のクラウドプラットフォームです。Next.js の開発元でもあり、静的サイトだけでなくサーバーサイドレンダリング(SSR)・Serverless Functions・Edge Computingまで対応します。

GitHubにコードをpushするだけで自動デプロイされ、CDNによる高速配信・プレビューURL・分析機能などが無料で使えます。

SSRServerlessEdgeCI/CDCDN
GitHub Pages

GitHub Pagesは、GitHubが提供する静的サイト専用のホスティングサービスです。HTMLファイルをリポジトリに置くだけで公開でき、Jekyll によるブログ生成も標準サポートします。

完全無料・設定ゼロで使える手軽さが最大の特徴で、ドキュメントサイト・ポートフォリオ・技術ブログに最適です。

Section 02
レベル別解説

🏫 中学生向け ── お店の棚で考えてみよう

「GitHub Pages」は文化祭で作ったポスターをそのまま貼り出す掲示板。「Vercel」はお客さんが来るたびに最新メニューを自動で更新してくれるデジタル看板。
▶ Vercelホームページを作ったとき、誰かが見るたびにサーバーが動いて最新情報を見せてくれる。ゲームのランキングみたいに、リアルタイムで変わるサイトが作れる。
▶ GitHub Pages作ったHTMLファイルをそのままインターネットに置いておくサービス。自己紹介ページや学校のクラブ紹介ページに向いている。むずかしい設定ゼロで使える。

📚 高校生向け ── プログラミング学習者へ

GitHub Pages は「静的ファイルをそのまま配信するCDN」、Vercel は「静的配信 ＋ サーバー処理まで担うフルスタックPaaS」と理解しよう。
▶ VercelReact・Next.jsで作ったSPAやSSRアプリを自動デプロイできる。APIサーバーも同じプロジェクトに置けるので、フロントとバックを別々に管理しなくていい。無料枠でも本格的な開発が可能。
▶ GitHub PagesHTML/CSS/JS・Vue・Reactのビルド済みファイルを公開するのに最適。プロジェクトのドキュメントや、JavaScriptだけで作ったポートフォリオサイトの公開に向いている。

💼 社会人向け ── 非エンジニアも知っておきたいポイント

GitHub Pages は「印刷済みチラシを棚に置くだけ」、Vercel は「注文ごとに最適なチラシを自動生成して渡す店舗」のイメージ。
▶ Vercel を選ぶ場面会社のサービスサイト、ECサイト、ダッシュボード、AIを使ったWebアプリなど「ユーザーごとに異なる情報を表示したい」ケース。スタートアップやプロダクト開発に最適。
▶ GitHub Pages を選ぶ場面社内ドキュメント、技術ブログ、オープンソースのドキュメントサイト、ランディングページなど「内容が固定されていて、誰が見ても同じでよい」ケース。

⚙️ ITエンジニア向け ── アーキテクチャ視点

GitHub Pages は Origin サーバーを持たない純粋な CDN エッジ配信、Vercel は CDN + Serverless Functions + Edge Runtime + ISR を統合した Composable Infrastructure。
▶ Vercel の強みNext.js の App Router と完全統合。RSC (React Server Components) のストリーミング、ISR (Incremental Static Regeneration)、Edge Middleware、Functions のコールドスタート最適化。GitHub Actions 不要で PR ごとにプレビューURLが自動生成される。
▶ GitHub Pages の強み完全無料・SLA制約なし・CNAME設定シンプル。Jekyll / Hugo / Astro などSSGとの相性が良く、Actions による独自ビルドパイプラインも構築可能。vendored assets の long-term caching に適している。

Section 06
初学者向けまとめ ── 結局どう使い分けるか
一言で言えば「動くかどうか」で決める

HTMLファイルを置くだけで完結するサイトなら GitHub Pages、サーバー処理・APIキー・動的なデータが必要なら Vercel。迷ったら下の判断軸を使おう。

VERCEL を選ぶ基準 APIを叩く処理がある
ログインや認証がある
DBのデータを表示したい
Next.js を使っている
AIを組み込みたい
GITHUB PAGES を選ぶ基準 HTMLをそのまま見せたい
サーバー処理が一切ない
ドキュメント・ブログ
完全無料で運用したい
設定を最小限にしたい
💡 学習ロードマップとして：まず GitHub Pages でHTMLの公開を体験 → Vercel で React/Next.js アプリをデプロイ → Serverless Functions で API を実装 → AIアプリの構築へ。この順番で学ぶと自然にスキルアップできる。
Section 07
用語集 ── この教材に出てきた言葉をやさしく解説

カテゴリをクリックして絞り込めます。

SSR描画方式
Server Side Rendering

ユーザーがページを開いたとき、サーバーがHTMLを作ってからブラウザに送る方式です。

たとえばSNSのタイムラインのように「開くたびに最新の内容が必要」なページに向いています。SEO（検索エンジンへの表示）にも強い。

Vercel ✓GitHub Pages ✗
CSR描画方式
Client Side Rendering

HTMLのガワだけ先に送って、ブラウザ（クライアント）がJavaScriptで画面を組み立てる方式です。

ReactのシンプルなSPAがこれにあたります。最初の表示は少し遅いですが、ページ遷移はスムーズです。GitHub Pages で動かせるのはこの形式だけです。

Vercel ✓GitHub Pages ✓（これのみ）
SSG描画方式
Static Site Generation

コードをデプロイする「ビルド」という準備作業のときに、あらかじめHTMLを全ページ作り置きしておく方式です。

ブログや商品カタログのように内容が頻繁に変わらないサイトに最適。配信が超高速で、GitHub Pages との相性も抜群です。

Vercel ✓GitHub Pages ✓
ISR描画方式
Incremental Static Regeneration

SSGの「作り置き」をしつつ、一定時間が経ったら自動でページを再生成できる仕組みです。Next.js独自の機能。

「毎回サーバーで作るほどでもないが、1日1回は最新にしたい」ニュースサイトや商品ページに向いています。Vercel でしか動きません。

Vercel ✓GitHub Pages ✗
RSC描画方式
React Server Components

Reactのコンポーネント（部品）をサーバー側で実行して、結果だけブラウザに送る仕組みです。

ブラウザに送るJavaScriptの量が減るので表示が速くなります。「この部品はサーバーで動かす」「この部品はブラウザで動かす」と役割を分担できるのが特徴。Next.js 13以降で使えます。

Vercel ✓GitHub Pages ✗
CDNインフラ
Content Delivery Network

世界中にファイルのコピーを置いておいて、ユーザーに一番近い場所から配信する仕組みです。

東京のユーザーが見るとき、アメリカのサーバーまで取りに行くより東京のサーバーから届けたほうが速い、という当たり前の発想を自動でやってくれます。VercelもGitHub Pagesも標準搭載。

Vercel ✓GitHub Pages ✓
Serverlessインフラ
Serverless Functions

「サーバーを常に動かしておく」のではなく、リクエストが来たときだけ処理を実行して、終わったら消える実行環境です。

たとえばOpenAI APIを呼び出す処理を、呼ばれたときだけ動くミニサーバーとして登録しておけます。管理不要・従量課金でコスパが良い。AWS Lambda が有名。

Vercel ✓（内蔵）GitHub Pages ✗
Edgeインフラ
Edge Computing / Edge Function

CDNのサーバー（＝エッジ）の上でコードを動かすことです。ユーザーの近くで処理が完結するため、往復の時間が極端に短いのが特徴。

たとえば「日本語ユーザーには日本語ページ、英語ユーザーには英語ページを返す」といった振り分けをエッジでやると、遅延なしで動作します。

Vercel ✓GitHub Pages △（静的ファイル配信のみ）
CI/CDインフラ
継続的インテグレーション / 継続的デリバリー

コードを変更してGitHubにpushしたら、テスト・ビルド・デプロイまでを自動でやってくれる仕組みです。

Vercelでは設定ゼロでこれが動きます。「pushしたら数秒で本番に反映される」体験がこれ。GitHub Pagesでも GitHub Actions を自分で書けば同様のことができます。

Vercel ✓（自動）GitHub Pages △（自己設定）
Next.jsフレームワーク
Reactベースのフルスタックフレームワーク

Reactで作った画面に、SSR・ルーティング・APIサーバー機能をまるごと追加したフレームワークです。Vercelが開発しています。

「ReactだけだとフロントのUIしか作れないが、Next.jsならバックエンドAPIまで同じプロジェクト内に書ける」というのが最大の利点。現代のSaaS開発では事実上の標準です。

Vercel ✓（フル機能）GitHub Pages △（静的書き出しのみ）
App Routerフレームワーク
Next.js 13以降の新しいルーティング方式

フォルダの構造がそのままURLになる仕組みです。たとえば app/blog/page.tsx というファイルを作ると、自動で /blog というURLが生まれます。

RSC（React Server Components）をフル活用できる設計になっており、Next.jsの最新機能はすべてApp Router前提です。旧来のPages Routerと設計思想が異なるため、学習時は混同しないよう注意。

Vercel ✓GitHub Pages ✗
Hydrationフレームワーク
ハイドレーション（水和）

SSRで作られた「静的なHTML」に対して、ブラウザのReactがJavaScriptを流し込んでインタラクティブに変換する処理です。

乾いたスポンジに水を含ませるイメージから「Hydration（水和）」と呼ばれます。この処理が終わるまでボタンを押しても反応しないため、高速化の重要なポイントになっています。

Vercel（SSR/RSC使用時）
APISaaS開発
Application Programming Interface

アプリ同士が会話するときのルール・窓口です。「このURLにこの形式でリクエストを送ると、このデータが返ってくる」という約束事。

たとえばOpenAI APIは「このURLにテキストを送ると、AIの返答が返ってくる」という窓口です。APIキーは「あなたが誰かを証明するパスワード」で、絶対に公開してはいけません（Vercelの環境変数に隠すのはこのため）。

Vercel ✓（サーバー側で安全に呼べる）GitHub Pages ✗（キー露出リスク）
AuthSaaS開発
Authentication（認証）

「あなたは誰ですか？」を確認する仕組みです。ログイン画面でIDとパスワードを入力するのが最もシンプルな認証。

現代のWebアプリでは「Googleでログイン」などのOAuth認証が主流です。Supabase Auth や NextAuth.js を使うと、Next.js + Vercel 構成に簡単に組み込めます。GitHub Pagesは静的サイトなので、認証の仕組み自体を持てません。

Vercel ✓GitHub Pages ✗
DashboardSaaS開発
ダッシュボード（管理画面）

ユーザーがログインした後に見る「自分専用の情報まとめ画面」です。売上グラフ・タスク一覧・通知などを一覧表示します。

ユーザーごとに異なるデータを表示するため、必ずSSRまたはCSRでデータを取得する必要があります。静的サイトには作れないため、Vercelが必要です。

Vercel ✓GitHub Pages ✗
